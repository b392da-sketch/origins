# Review 037 — G4a performance at gate scale and documentation drift

Reviewed main at `fd7412f`, including the approved gate plan. **Hold the full dispatch.** The current workflow has no demonstrated margin for the heaviest histories, and checkpoint and report memory grow with history length. The 64-disease ceiling also needs a recorded disposition before check 10 can be interpreted. The measurement, state and replay blockers from reviews 034–036 still apply.

## Ranked findings

### 1. The five-stage workflow can run out of time and publish a partial gate

- **Where** — `gates/plan.py:17–42`, `gates/run_job.sh:15–38`, `gates/g4.py:232–275`, `.github/workflows/gate.yml:210–267`, `gates/g4_report.py:22–23,74–86`.
- **What is wrong** — Five stages give each history 22.5 nominal hours of budgeted work, including reload time. The fifth stage uploads completed JSON from `out/` and drops any remaining checkpoints from the artifact chain. Expiration returns normally, and the report computes across whatever completed records arrived. It prints the observed counts but has no comparison with the requested planet, seed and arm roster.
- **Why it matters** — A history can fall out of the denominator precisely because its world became large or expensive. The published results can then favour smaller or faster worlds. Default packing puts up to three histories on the same 16 GB runner. CPU headroom alone cannot establish that the three concurrent saves and restores fit.
- **How sure you are** — Certain about the control flow and missing completeness check. Likely that the current defaults are unsafe for some heavy histories. Actual run completion is unverified.
- **How to see it** — Follow the worker's budget return through the shell script and stage 5 artifact upload. The approved plan's late planet-3 sample ran at **6.04 s/year**, with another **185 s** to build the record. At that pace the final 6,000 years alone take **10.1 hours**, leaving **12.4 hours** for earlier years and resume overhead. A history reaching the 30,000-year ceiling has an average budget of **2.70 s/year** before reloads. G3 planet 4 seed 1 used **9.92 hours** for 24,958 years under the earlier model. These figures describe different histories and are capacity bounds, not an estimate obtained by adding their runtimes. Exercise a forced timeout in the final stage with a tiny budget and check the continuation artifact and report status.

### 2. Disease history can exhaust the runner at save, restore or final export

- **Where** — `origins/sim/disease.py:71–95,460–475,548–555`, `origins/persist.py:34–46,59–131`, `gates/g3.py:146–176`, `gates/g4.py:224–229,262–270`.
- **What is wrong** — Every disease-cell year is kept in an in-memory list and included in one JSON metadata member. Save constructs a second nested structure and a JSON representation. Restore parses the complete member and copies every disease row again. Final G3/G4 export copies and sorts the log and builds spells which still retain a pair of integers per spell-year. The compressed checkpoint size conceals these allocations.
- **Why it matters** — At a steady 1,000 logged disease-cell pairs per year, the last 6,000 years alone would add 6 million rows. This is a sensitivity case, not a predicted prevalence. A runner can survive annual stepping and then run out of memory exactly when it needs to save or finish. Sampling away disease-years indiscriminately would break check 10's full spell and first-contact evidence.
- **How sure you are** — Certain about growth and copying. The frequency and size of dense late histories remain unmeasured.
- **How to see it** — In a new planet-4 world, assign one million 17-field rows to `w.dz_log`, then call `persist.to_file(..., fast=True)` and restore in the same process after dropping the original world. Peak RSS reached **331 MiB** after construction, **645 MiB** after save and **680 MiB** after restore. The metadata member was **52.9 MiB** before compression and the whole ZIP **4.25 MiB**. Save and restore took **5.7 s** and **2.0 s** on this sparse fixture; real checkpoints also contain the historical arrays and events. See the fixture below.

### 3. The aggregate report retains three parsed copies of the main records

- **Where** — `gates/g4_report.py:22–23,74–97`, `gates/g3_report.py:18–22,84–111`, `gates/g2_report.py:_load`, `.github/workflows/gate.yml:250–288`.
- **What is wrong** — G4 keeps all records resident, writes the main arm as full JSON for G3, then G3 reads those records and writes them again for G2. When G2 runs, the caller frames still retain the other parsed copies. These copies include G4-only census and disease structures. A report exception is converted into a line of output and the workflow proceeds to publication.
- **Why it matters** — Successful individual histories can still end in an aggregate report failure or a published failure note alongside their raw records. The branch publication also pushes individually uncompressed JSON files; GitHub's ordinary Git file limit is 100 MiB per file. Artifact compression does not raise that limit.
- **How sure you are** — Certain about duplicate parsing and publication behaviour. Peak with all 70 G4a records and the largest individual record are unverified.
- **How to see it** — Load planet-4 seeds 1–5 from the archived G3 run-3 records into one retained Python list. About **34 MiB** raw raised process peak RSS from **8 MiB to 261 MiB**, for a single parsed copy. The full archived G3 set is about **369 MiB** on disk before G4 fields. Use the G4 report call stack to see the additional copies. The limit on an ordinary push is documented under [GitHub's file size limits](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github#file-size-limits).

### 4. After 64 named diseases, new disease emergence stops for the rest of the history

- **Where** — `origins/sim/disease.py:44–55,98–117,357–384`, `origins/params.py:393–398`, `docs/M4_SPECIFICATION_v1.md` §6 and check 10, `docs/M4_BUILD_NOTES.md` “Diseases from animals, as built”.
- **What is wrong** — The fixed array width also limits the lifetime number of distinct diseases. `_emerge` returns when the registry reaches 64, including if all prior diseases are currently absent from people. No saturation field is reported. I found the ceiling in the code and no matching design decision in the spec, build notes or gate plan.
- **Why it matters** — Check 10 includes wild and herd starts and their outcomes. After saturation the existing reservoirs continue, while all new starts are censored. At a sustained 2.6 million people the default wild-emergence term alone gives about **0.052 candidate starts per year** in expectation before the cap, or 64 in roughly **1,230 years**. At 500,000 it is roughly **6,400 years**. Herd-derived starts can use slots sooner. These are simple fixed-population calculations; the gate's actual time at each population is unknown.
- **How sure you are** — Certain about saturation and the consequence. Whether individual G4a histories reach it is unverified.
- **How to see it** — Call `_emerge` with `len(w.diseases) == ND_CAP`, an empty circulation array and positive population. The return precedes both emergence paths. In a targeted test with a forced successful wild emergence draw, the creation function was called once at 63 and zero times at 64. Check the last new-disease event against the last simulated year in any pilot reaching the ceiling.

## Performance at the G3 population scale

A single-process planet-4 fixture used the 40,962-cell grid, 13,000 added 200-person group bands and three original bands (**2,600,090 people**). Cells were sampled uniformly from land with seed 143. These are isolated, one-pass timings on this workspace with one NumPy thread. The bands lack late-run farm, language and event histories. Actual G3 run-3 planet-4 records had around 5,000–6,300 live bands at their recorded peaks, so the fixture deliberately stresses band work. Neither these timings nor the historical band counts predict the G4a distribution. Continuing the artificial fixture through four engine ticks took about 154 s and peaked at 470 MiB, but it lost over half its population and raised four invariant failures. That run measures an artificial shock and supplies no steady-state timing.

| Phase | Observed elapsed | Frequency and cost driver |
|---|---:|---|
| Technology | 1.58 s | Annual, at harvest. Eligibility, need and teaching use band-by-technique work and neighbourhoods. Technique-effect lookups in other phases also allocate quality arrays at historical band capacity. A cut-off can trigger extra prerequisite evaluations. |
| Directed traders | 2.26–4.63 s cold, 0.51–1.07 s on immediate repeat | Annual, after neighbour exchange. 100, 300 and 600 provisioned seats, up to 12 route candidates per seat. Straight-line gravity compares each trader seat with every seat. A* cache misses, round trips and toll detours drive the variable part. An immediate repeat bounds a favourable cache case. Resume starts a new process without the cache. |
| Down-the-line exchange | 0.13 s | Annual, for dispersed bands. Candidate counts are quadratic within a crowded cell and multiply across adjacent cells. A single cell with 2,000 bands would generate 1,999,000 same-cell pairs, about 46 MiB for the three int64 pair arrays alone, plus Python lists and exchange temporaries. |
| Named disease | 0.07 s with none, 0.10 s with eight seeded on one cell each | Annual, in the M1 outbreak season. Dense circulation also visits disease-cell and band combinations and records the rows in finding 2. |
| Land update | 0.014 s | Annual, at harvest. Cell-wide vector arithmetic. This timing excludes upkeep and effects in other seasonal phases. |
| Place naming | 0.060 s cold, 0.031 s on a later pass | Every ten years at current defaults. The fixture has no late conquest or deep place history. The pass reads recent events back to the previous naming pass. The latest-name cache helps lookups. |
| G4 census | 0.002 s ordinary year, 0.050 s century year | All living bands are visited even when the century sample is ultimately limited to 2,000. The annual farm sweep also scales with previously farmed cells. |

Technology and directed routing dominate the added phases in this fixture. The real late planet-3 trial in the build notes also attributed about **0.83 s/year** of **4.35 s/year** to traders after the shortlist revision. The remaining time in that trial includes the base simulation. At the end of a history, full scans of the cold event store, explanation indexing and record materialization are separate costs. The gate plan's current 185-second record build includes this work for a smaller late history; G4's reported per-history seconds exclude final record construction. See `origins/engine.py:12–38`, `origins/sim/technology.py:593–675,807`, `origins/sim/trade.py:502–531`, `origins/sim/traders.py:150–205,274–347` and `gates/g4.py:117–229`.

### Memory stock and growth

- **Band arrays follow historical IDs.** Technology, goods and partner histories, disease immunity and dates, and land accounting total approximately **1,742 bytes per allocated row** in the fixture's dtypes, excluding inherited arrays, dictionaries and scratch memory. At a common capacity of 1,048,576 IDs that is **1.70 GiB per history**. At 2,097,152 it is **3.40 GiB** or **10.2 GiB for three concurrent histories**. These are capacity scenarios, not measured end-of-run ID counts. Growth reallocates individual arrays and temporarily holds the prior allocations. Dense disease and land persistent cell arrays add about **19.5 MiB** for planet 4. The sparse phase fixture's peak RSS was **276 MiB** through the isolated passes.
- **Events grow on disk and partly in RAM.** Four million cold offsets alone are about **30.5 MiB**. The newest 20,000–50,000 events are kept as dicts, and all `outbreak` events remain in RAM, including those emitted by the named-disease system. The cold JSONL still grows on disk and is scanned, recompressed and restored. The checkpoint streams events. It builds the full metadata member and reads arrays as a full ZIP member on restore. Historical individual and band records also grow with births, unfolding and band creation. Group compaction removes inactive rows; review 035 identified an end path that leaves rows active.
- **Other records grow with time or turnover.** The census has a per-century limit and can still reach **600,000 rows per history** at 30,000 years. The annual food-shortage and probe series grow with years. Place names keep layers, language keeps change history, and the writing log keeps rows for holders or scribes at each ten-year pass. The exporter retains all still-available history for qualifying polities as well as its sample. The input polity log is capped at 3 million rows. Invention and loss records are accumulated in full and adoptions are sampled only after the event scan. The route-opened and toll-evasion registries grow with historical polity pairs and triples. In contrast, repeated exchange, gift, trader-route and war detail logs are thinned via `log_row`.

## Release criteria

1. **Before dispatch:** resolve the open correctness blockers from reviews 034–036, the lifetime disease ceiling and the incomplete-roster path. Make an unfinished stage retain a usable checkpoint or fail as incomplete, with the missing history identified. Use one history per job for the heavy slice until packing has measured memory headroom.
2. **Prove the heavy path with a bounded slice:** measure seasonal and annual timing, living and allocated band counts, disease rows, RSS, disk peak, and save, restore and final export time on a representative late planet-4 checkpoint. Establish the stage count from the measured budget, including cold resumes. The available benchmarks establish plausible failure modes but cannot certify an individual G4a history.
3. **Prove reporting separately:** measure aggregate memory with full-roster-sized records, avoid parsing the G4-only payload repeatedly, and verify that publishing the largest result succeeds. Keep disease-year evidence needed by check 10 while bounding working memory.

## Checked and sound

- Cold event JSONL is streamed in checkpoint writes. Previously measured cause chain indexing removed a full event scan per band lookup. The remaining scans are a whole-history cost, not a return to the original per-lookup path.
- Census sampling has a deterministic per-history/year random seed and a per-century output cap. Review 036 covers the separate issue of a saved array being updated while probing.
- The road cache is bounded and carries no simulation state. Thinned repeated trade and war detail logs retain historical coverage at capped size.
